# Issue #2658 implementation plan

Issue: https://github.com/xcv58/Tab-Manager-v2/issues/2658

Baseline: `master` at `81f86f8e`, clean working tree; `git pull --ff-only`
reported already up to date on 2026-10-08.

## Outcome and scope

Implement both approaches proposed in the latest maintainer comment:

- A window-header menu with “Move selected tabs to beginning” and “Move
  selected tabs to end”.
- Two temporary full-height header drop areas while dragging: left
  “↑ Beginning”, right “↓ End”. Highlight the hovered half with an outline
  and a short placement hint. Restore the normal header on drop or cancel.

Keep insertion between tab rows and the existing top/bottom insertion strips.
The additional keyboard shortcuts suggested in the discussion are outside this
change.

## Implementation steps (recorded before implementation)

1. Add a shared `DragStore` operation for moving the current selection to a
   window edge. Reuse `dropAt` suspension, selection cleanup, grouping behavior,
   and layout preservation. Reject empty selections and unsupported windows.
2. Add explicit window-edge placement to `dropAt`. Use index `0` for beginning
   and the browser append sentinel `-1` for end, so a same-window selection of
   nonadjacent tabs appends together in existing order. Keep the append sentinel
   for every block in a mixed group/tab move. Preserve whole selected groups,
   detach partial fragments, and respect browser pinned-tab boundaries.
3. Add an observed header drop-area component using the existing React DnD tab
   type. Overlay the normal header without changing its dimensions. Each half
   gets a clear label, theme-aware outline/background and hover hint. Retain
   the existing narrow top insertion strip; layer the drag overlay above it so
   both halves accept drops throughout the header height. First-row insertion
   remains available through the normal row target.
4. Add a compact window actions menu using the existing menu and icon-button
   components. Disable both moves without a selection or for unsupported
   destinations. Close the menu before invoking the shared move operation.
5. Add focused, behavioral regression coverage for edge placement, same-window
   ordering, selection cleanup, whole/partial groups, unsupported destinations,
   drop targets and menu controls. Add test code without executing it.
6. Format changed files, inspect the final diff, and run `pnpm build` only.

## Acceptance criteria

- The destination can be reached through its header without scrolling to the
  bottom of a long tab list.
- Beginning/end moves work within one window and across windows, preserve
  selection order within browser pinning constraints, and use all destination
  tabs even when search or group collapse hides rows.
- Entire selected groups stay intact; partial selections leave their groups
  when moved to window space. Existing row-level drops keep their behavior.
- Header targets appear only while dragging and disappear on drop/cancel.
  The full header height is usable; the chosen half has visible feedback.
- The menu supports the shared menu's keyboard navigation and focus return.
  Empty selection and unsupported window types cannot trigger a move.
- Successful moves clear selection and preserve the existing manual-layout
  behavior; failures retain selection and resume the window store.

without explicit human approval. Added tests remain unrun in this task.

This changes snapshot-sensitive window-header controls, layout, and hover

pending, and affected `chromium-linux` baselines may need an approved follow-up.
Do not refresh snapshots or claim full verification from the build alone.

Browser append semantics: the Chrome tab and tab-group APIs document `-1` as
placement at the end:
https://developer.chrome.com/docs/extensions/reference/api/tabs#method-move
